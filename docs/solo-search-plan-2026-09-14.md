# 大連鎖を繰り返す探索AIの実施計画

決定日: 2026-09-14。実装担当はこのCodexタスクが行う。この文書は設計と実験手順を定め、実行後は同じ条件の結果と未達条件を追記する。

## 1. 目的と開発範囲

一人プレイで10連鎖以上を繰り返し発火し、12連鎖以上も増やす。主な利用環境は現在のWebアプリとし、Macのブラウザで1手を無理なく計算できることを目指す。対戦、相殺、おじゃま、操作入力の速さは対象に含めない。

新しい探索エンジンを `solo-search` として実装する。v14などのプロファイルを追加せず、旧vシリーズの加点・減点の積み重ねも継承しない。旧エンジンは比較と初期学習データの生成に限定して凍結し、新エンジンの実行時には呼ばない。旧ファイルの削除は今回の移行の前提にしない。

探索は新しくするが、盤面のルール、既存の高速盤面表現、リプレイ表示は再利用する。新エンジンが採用条件を満たした時点で、一人プレイの標準エンジンを切り替える。

## 2. 探索方式の決定

「小さなニューラルネットワークで途中盤面を評価するビーム探索」を採用する。ニューラルネットワークは置き場所を直接決めず、配置・消去・落下を正確にシミュレーションした後の盤面を採点する。毎手、置き場所は探索で決める。

現在の問題は、探索途中の評価で仮想発火を省く一方、最後に残った候補だけを高精度に評価する構造にある。新系統では長期の大連鎖実績を学習した同じ評価関数を、枝刈りの前と最後の比較の両方に使う。これによる改善は仮説であり、後述の比較実験で確かめる。

| 項目 | 最初に実装する設定 |
| --- | --- |
| 観測情報 | 盤面、現在の組、NEXT2組だけを渡す。 |
| 探索深さ | 現在手を含む3手とする。実際に渡されたNEXTが少なければ、その分だけ浅くする。 |
| Beam Width | 実測した既定値は22とする。比較用に32、48、64も受け付ける。 |
| 途中評価 | 全ての展開盤面に、小型の学習済み評価関数を適用する。 |
| 候補の保持 | 各初手について生存する最良経路を1つ確保し、残りを全体の評価順に埋める。 |
| 重複除去 | 同じ深さ・同じ初手・同じ盤面なら、累積報酬が高い経路を残す。ハッシュ一致後に盤面も比較する。 |
| 最終決定 | 最後の探索段階の値から初手を選ぶ。探索途中の値をそのまま最終候補と混ぜない。 |
| 未知ツモのサンプリング | 最初の20時間の計画では実装しない。未知ツモの平均的な影響は学習した値で扱う。 |
| 仮想発火の全列挙 | 本番の各ノードでは実行しない。診断と旧AIの比較に限定する。 |

初手の種類は最大22なので、Beam Width 22以上なら各初手の最良経路を確保できる。生存経路がない初手は枠を確保しない。死亡ノードは展開せず、実際の初手で即死を避けられる場合は即死手を選ばない。どの初手も先読み中に死亡する場合の比較も、終端報酬と決定的な同点処理で定義する。

各深さdの経路の値は、実際に発生した報酬の割引和と、配置後盤面の将来価値を足す。

`Q_d = Σ(i=0..d-1) γ^i r_i + γ^d V(配置後盤面, まだ見えているNEXT)`

`γ = 0.99` とする。終端ではVを0とし、死亡の減点は一度だけ加える。生存経路は同じ深さ同士で比較する。実発火の報酬は累積部分だけに入り、Vの教師信号にはその発火を再度含めない。

モデルに見せるNEXTは探索で消費するたびに減らす。深さ1の配置後には元のNEXT2組、深さ2では1組、深さ3では0組が残る。シミュレータが持っている、その先の実ツモを補充して評価してはいけない。

## 3. 評価関数と学習方法

最初のモデルはMLPとし、入力438、隠れ層64・32、出力2とする。約3万パラメータに抑える。隠れ層はReLU、計算はまずfloat32で統一する。

- 盤面は6列×14行×5状態のone-hotで420要素とする。状態は空と4色で、おじゃまは入力対象外とする。
- その配置後に見えている最大2組を、1組あたり色8要素と既知・未知を表す1要素で符号化する。合計18要素とする。
- 出力は「次の128手で得る割引報酬」と「128手以内の死亡確率」とする。死亡確率は補助学習と診断に用い、探索値に別の死亡減点として重ねない。
- seed、通算得点、ゲーム番号、隠れた実ツモは入力しない。色置換によるデータ拡張は行う。死亡列が左右対称でないため、左右反転は行わない。
- JavaScript側も同じ入力順・ReLU・重みを使う。重みだけをエクスポートし、ブラウザではWeb Worker内のCPUで探索する。WebGPUを本番動作の必須条件にしない。

学習報酬は実際の発火だけから作る。1手でc連鎖した場合の効用u(c)を以下に固定する。

| 実際の連鎖数c | u(c) |
| --- | ---: |
| 0〜9 | 0 |
| 10 | 1.00 |
| 11 | 1.25 |
| 12 | 1.50 |
| 13 | 1.75 |
| 14以上 | 2.00 |

学習時の報酬rはu(c)とし、死亡時に追加で−4を与える。死亡後の将来価値は0とする。最大連鎖、仮想発火、積んだぷよの数、ゲーム得点による報酬は加えない。14連鎖1回と10連鎖2回を同じ効用にすることで、一度だけ大きく消すことへの偏りを抑える。

Vの教師信号は、配置後の次手から128手分の実際のrをγで割り引いた合計とする。TD学習や探索値の自己模倣から始めず、実プレイの結果を使う。128手は複数回の大連鎖を含めるための設計値であり、この20時間では調整対象にしない。

学習は次の順序で行う。

1. GPUを開始する前に、凍結したv13で学習専用seedを使い、64ゲーム×1024手までの初期軌跡をローカルCPUで集める。旧AIの評価値は教師にせず、盤面・実行動・実連鎖・死亡だけを使う。初期データには、異なるゲームから合計100件以上の10連鎖以上の発火があることを確認する。不足時はCPUで追加収集する。
2. 初期MLPを学習し、これを使った新しい探索で一人プレイのデータを増やす。初期モデルも比較対象として保存する。
3. 「固定したモデルで生成→実績から再学習→開発用seedで比較」を最大4回行う。各生成バッチの途中ではモデルを変更しない。各回、最新モデルと最良モデルを別々に保存する。
4. 生成時だけ5%の確率で、生存する上位3初手のいずれかを等確率で選ぶ。それ以外と全ての評価時は最良手を選ぶ。

モデルを学習するデータはゲーム単位で90%/10%に分け、後者は損失の確認と早期終了にだけ使う。これはエンジン選択用の開発seedとは別にする。隣接する盤面、同じ軌跡の再開分、色置換した複製を異なる区分へ分散させない。

初回の更新では初期データ30%・新データ70%、以降は初期データ10%・新データ90%を目安にする。新データは最新50万配置を保持し、ゲーム内の有効な配置から一様に抽出する。大連鎖直前だけを過剰に抽出しない。各入力は既知NEXT数0・1・2を等確率に選び、先頭からその数だけ残す。

初期設定はAdam、学習率0.001、batch size 1024とする。損失は将来報酬のHuber lossと、死亡確率のbinary cross-entropyの0.1倍を足す。学習率や層数を大量探索せず、損失・校正・実プレイを確認する。

1ゲームの生成は1024手で区切る。末尾で128手分の未来を観測できていない配置は、そのまま0埋めして学習させず、教師データから除く。実死亡で終わった場合だけ、その先を終端の0として確定する。生成を途中保存する際は未確定の128手も保存する。

有効な新規教師データは200万配置を目標、50万配置を最低目安とする。ただしGPU計測前に達成を約束しない。発火イベント件数と異なるゲーム数も記録し、色置換や同じデータの再学習回数を新規配置数に数えない。

## 4. シミュレータのルールと一致検証

調査時点の基準コミットは `8db100a412568e12f1dadd239611c349e41bc353` である。Solは着手時の差分を確認して実際の基準コミットを記録する。

ルールは現在の `src/core/engine.js`、`board.js`、`constants.js` と既存テストに合わせる。古い `docs/web-simulator-spec.md` には現在の実装と異なる死亡条件や消去範囲が残っているため、その文章からGPU版を再実装しない。

現実装では内部6×14、保存対象13段、通常消去対象12段で、14段目以上へ置かれるぷよは保存されない。配置したセルが0始まりの(x=2,y=11)に当たると、連鎖解決前に死亡する。これは現実装との比較条件であり、実際の市販ゲーム全体の仕様を断定するものではない。

GPU版は4色・おじゃまなしに限定してよいが、上端、横置きの個別落下、同色組の重複、全消し、連鎖数、得点は基準実装と一致させる。意図的なルール改善は別実験に分ける。

GPUで大量生成を始める前に以下を通す。

- 既存fixtureと境界ケースに加え、実際の合法なプレイ軌跡から採った1万盤面について、16色組×全配置を比較する。低い盤面、高い盤面、発火直前、発火直後を含める。
- 配置後盤面、死亡、連鎖数、得点、全消しを整数で完全一致させる。GPUの色連結判定や連鎖ループの上限で処理が打ち切られた場合は、成功扱いせずエラーにする。
- 32本以上の連続軌跡で、同じツモと同じ行動をGPU版とJS版に入力して毎手の盤面を比較する。
- 1万入力についてMLPのJS/GPU出力も比較する。目安は `abs_error <= 1e-4 + 1e-4 * abs(reference)` とし、順位差が出た場合は同点付近か実装差かを調べる。
- 開発用32ゲームをGPU探索とJS探索の両方で動かす。最初に行動が異なった盤面を残し、入力、同点規則、計算精度を追う。大きな差を「GPUだから」で許容しない。

同点では列・向きから決めた固定action ID、続いて固定経路順を使う。GPUの不安定なtop-k順序に依存しない。

## 5. KaggleでGPUを使う方法

既存の `training/train_value_stream.py` はNode.jsでデータを生成しており、そのゲームシミュレーションはCPUで動く。KaggleのGPUを有効にするだけではGPUシミュレーションにはならない。

新しい実験環境はPython/JAXで実装する。配置、消去・落下、MLP評価、ビーム選択をGPU上でバッチ処理する。盤面数・候補数は固定形状にしてマスクで有効・無効を表す。ゲームと候補をまとめて処理し、毎盤面をPythonから1個ずつGPUへ送らない。JAXの `jit` と `vmap` はこの実装に使える。[JITの公式説明](https://docs.jax.dev/en/latest/jit-compilation.html)、[自動ベクトル化の公式説明](https://docs.jax.dev/en/latest/automatic-vectorization.html)

最初は1GPUあたり64ゲームの同時進行から始め、32・64・128を短く測って選ぶ。盤面解決の実装はCPUで動くJAX版として先に検証し、GPUを有効にしたまま通常のコーディングをしない。巨大なゲーム全体を展開してコンパイルせず、固定長の処理単位とループで進める。

T4が2枚割り当てられた場合は、1GPUごとに独立したゲーム群を処理する。最初はモデル並列や分散勾配同期を導入しない。使用するGPUを明示し、JAXのメモリ確保量も制限して、両方のプロセスが同じGPUを使わないようにする。T4 x2などの選択肢と、セッション開始によるGPU枠消費はNVIDIAのKaggle案内でも説明されている。[NVIDIAの案内](https://docs.nvidia.com/datascience/deployment/nightly/platforms/kaggle/)

最初のGPU試行では、以下を別々に記録する。

- 初回コンパイルと準備に使った秒数を記録する。
- 全探索を含む「実際に置けた組数/秒」を測る。死亡後の無効マスクや探索ノード数を配置数に含めない。
- 盤面解決、MLP、候補選択、ホスト転送の所要時間を調べる。
- GPU使用率とメモリを記録するが、これだけで高速化成功とは判定しない。
- 反復処理の計測はGPU完了を待ってから終了する。コンパイル込みの時間と定常速度を分ける。[JAXの計測手順](https://docs.jax.dev/en/latest/benchmarking.html)

1GPUあたり100配置/秒を初期の実用目安とする。100未満なら、計測値から最低50万の有効教師データと最終評価が残り枠に収まるかを再計算する。収まらない場合は、まずバッチと転送を直す。GPU枠を1時間分使っても正しく動く最小バッチができない場合、GPUジョブを終了しCPUで修正する。

GPU利用率を上げるためにネットワークを大型化したり、シミュレーションがCPUのままなのにGPU生成済みと報告したりしない。GPU版が成立しない場合は、その制約と計測結果を残して計画の変更を提示する。

## 6. ツモ、seed、評価データの固定

現在の4色乱数方式を条件として固定する。評価用のツモ列は既存 `src/core/randomizer.js` で事前生成し、ファイルに保存する。各方式に同じ列を渡すので、JSとJAXで乱数実装が異なっても比較条件は揃う。

seed名は `solo-search-20260914/{区分}/{index}` とする。区分は `train`、`dev`、`test`、`latency` を分け、ツモファイルのSHA-256と一覧を実験前に保存する。旧データを再利用する場合も、seedとツモ列の重複を調べる。

AIには現在手とNEXT2組だけを渡し、列全体や環境のseedを渡さない。「NEXT2まで同じ、さらに先だけ異なるツモ列」で同じ盤面の判断が変わらないことをテストする。探索用の乱数を追加する場合も実ツモ生成の乱数とは分離する。

開発評価は64seed、最終評価は未使用128seedを使う。全て空盤面から1ゲーム1000手とし、死亡後はそのゲームを再開しない。残りの予定手数は発火0として集計する。死なずに1000手到達した場合は終了とする。

最終testのツモ列は準備時に固定するが、学習、モデル選択、枝幅調整、例の手直しには使わない。testに進む前に、モデルのハッシュ、探索設定、採用判定、評価コードを固定する。途中結果を見て評価を打ち切ったりseedを選び直したりしない。

## 7. 大連鎖の連発を測る方法

主指標は、予定1000手あたりの大連鎖効用とする。

`U1000 = 1000 * Σ u(実発火の連鎖数) / 全ゲームの予定手数`

128ゲームなら分母は128000で固定する。生きて実行できた手数だけを分母にすると、早死にした方式が得をするため、採用評価では使わない。終了時に盤面に残っている仮想連鎖は得点にしない。学習の−4やγは評価のU1000には混ぜず、死亡は別指標でも示す。

併記する指標を以下に固定する。

| 指標 | 集計方法と役割 |
| --- | --- |
| 10+、11+、12+、13+、14+発火数 | 予定1000手あたりで示し、連鎖の大きさと回数を分けて判断する。 |
| 連発できた区間の割合 | 各ゲームを200手ずつ5区間に分け、10+が3回以上あった区間の割合を示す。死亡後も区間を分母に含める。 |
| 発火後60手以内の再発火率 | 手数940以前の10+発火を対象に、その次の60手で再び10+が出た割合を示す。途中死亡は失敗、該当発火0件なら未定義として件数を示す。 |
| 大連鎖が出ない最長手数 | 開始から最初の10+まで、発火間、最後の発火から予定1000手までを全て含める。10+がなければ1000とする。 |
| 死亡率 | 1000手到達前に死亡したゲームの割合を示す。 |
| 初回10+までの手数 | 未達ゲーム数も併記し、成功ゲームだけの平均で評価しない。 |
| 1〜9連鎖、ゲーム得点、最高連鎖 | 診断用に残し、主指標の代わりにしない。 |

旧v13との比較は、調査時の標準設定 `depth=3, beamWidth=48, sampleCount=8, sampleDepth=4, sampleBeamWidth=8, sampleTopK=12, sampleWeight=1, dedupe=true` を基準にする。旧v13のサンプリングOFFも速度比較用に固定する。過去のREADMEに書かれた速度や連鎖率を今回の測定値として使わない。

開発評価は最初の16seedで明確に劣る候補を落とし、残った候補は64seed全てで評価する。最終評価はdevで選んだ新系統1候補、v13標準、v13サンプリングOFFを同じ128seedで測る。旧AIの長いCPU評価はGPU開始前からローカルで進めてよい。GPU枠の配分とは別に、そのCPU経過時間も見積もる。

統計はゲームseedを単位にした対応付きbootstrapを10000回行い、U1000の差と比の95%区間を出す。連続する各手を独立サンプルとして扱わない。死亡率なども分母と不確実性を併記する。検証用seedで比較した候補数と選択経緯を記録し、最終testを見て別候補に差し替えない。

## 8. ブラウザでの速さと採用条件

GPUの大量生成速度と、ブラウザの1手の待ち時間は別々に測る。主な速度基準はユーザーのMac・固定したブラウザ・Web Worker・他の重い処理を止めた状態で測る。端末、OS、ブラウザ版を記録する。iPhoneは同じ試験の補足対象とし、未実施なら未検証と明記する。

latency用1024盤面を低い盤面、高い盤面、発火直前、発火直後から均等に用意し、モデル選択前に固定する。同じ盤面セットを全方式に与え、初回読み込み、ウォームアップ後の中央値・p95・p99を示す。同じ盤面を繰り返すキャッシュ有利な試験だけにせず、エンドツーエンドの1ゲーム1000手の計測も行う。UIアニメーションや自動設置の待ち時間は探索時間と別に記録する。

目標は中央値100ms以下、p95 200ms以下、p99 500ms以下とする。これは実測値ではなく採用のための目標値である。タイムアウトした判断も測定から除外しない。まず固定ノード数の探索で性能を測り、時間で探索を途中打ち切る仕組みは今回追加しない。

通常採用には、最終testで次を満たすことを求める。

1. 上記のブラウザ速度目標を満たす。
2. v13標準に対してU1000が10%以上高く、対応付き差の95%区間の下限が0を超える。
3. 10+発火率はv13標準以上、12+発火率はv13標準の95%以上とする。死亡率の悪化は2パーセントポイント以内とする。

別の採用経路として、U1000比の95%区間の下限が0.95以上で、p95がv13標準の半分以下なら「大連鎖能力を概ね維持した高速化」として採用できる。この場合も速度目標と12+・死亡率の条件は満たす。これは連鎖能力の向上とは別の結果として報告する。

どちらにも達しなければ、新系統の実装・学習結果は残すが、性能改善を達成したとは報告しない。指標を後から変えて勝ったことにしない。

## 9. 20時間分のGPU枠の使い方

残り約20時間はユーザー申告に基づく予算とする。現在のアカウントの残量、T4の割当枚数、枠の減り方はこの設計作業では確認していない。実行開始前と短い試行後にKaggleの残量を確認する。下表は壁時計時間や単純なGPU枚数×時間ではなく、Kaggleの残量表示で消費する時間分である。計測できるまで、2枚のGPUなら20時間×2の計算を使えるとは仮定しない。

| 作業 | 予算 | 終了時に残すもの |
| --- | ---: | --- |
| GPUでの一致確認・速度測定 | 1時間分 | 一致レポート、配置/秒、残り枠で処理できる量の見積もりを残す。 |
| 初期モデルの学習・新探索の確認 | 2時間分 | 初期モデル、少量の実プレイ、JS推論の一致と速度を残す。 |
| 生成と学習の反復 | 8時間分 | 最大4回のモデル、データ、devでの実績を残す。 |
| 必要な比較と設定選択 | 3時間分 | 構造の比較、Beam Widthの選択、最終候補を残す。 |
| 最終評価・書き出し・回収 | 3時間分 | 未使用seedの評価、ブラウザ用モデル、検証済み出力を残す。 |
| 復旧のための予備 | 3時間分 | 失敗からの再実行にだけ使用し、通常学習では消費しない。 |

ローカルでの実装、CPU一致試験、初期データ生成、旧AIの比較、文書作成にはGPU枠を使わない。最終評価・回収用の3時間分と予備3時間分は学習延長に流用しない。使わずに済んだ枠は残す。各GPUジョブは準備・コンパイル・保存込みで最大4壁時計時間程度に区切り、実行環境の上限と残量がさらに短ければそちらに合わせる。

学習したモデルの実プレイが2回続けてdevで改善しなければ、残りの反復を停止し、最良モデルの比較・検証へ移る。学習損失だけが下がっていても続行理由にしない。

比較は次の3つに限定する。変更する要因以外は、モデル・深さ・Beam Width・seedを揃える。

- 初期学習モデルと、追加生成で更新したモデルを比較する。
- 学習評価を各段階で使う場合と、最後だけで使う場合を比較する。後者の中間順位は事前固定の簡単な組数・高さ評価を使い、比較中にその重みを調整しない。
- 各初手の最良経路を確保する場合と、単純な全体上位Beamの場合を比較する。

これらを終えてからBeam Width 22・32・48・64を比べる。今回の開発測定では22と32を比較し、48と64は未実施として残す。新しい探索方式、モデル大型化、MCTS、未知ツモの追加サンプリングを同時に試す総当たりには広げない。

## 10. 保存、回収、再開

Kaggleではバックグラウンドの実行として投入し、CLI/APIで状態と出力を確認する。公式CLIには `kernels push`、`status`、`files`、`output` がある。実際の導入済みCLIで利用可能な引数を確認して使う。[Kaggle公式CLI](https://github.com/Kaggle/kaggle-cli/blob/main/docs/kernels.md)

このMacではKaggle CLI 2.2.4を `uv tool` で導入し、`ikakun624` としてOAuth認証している。2026-09-13の実験では、実行中のNotebookが正常でもアクセストークンが切れ、`kernels status` がNotebook名や非公開設定の問題に見える `Permission 'kernels.get' was denied` を返し、別のコマンドは `Authentication required` を返した。エラー文だけでNotebookの消失やslug違いと判断してはいけない。

各投入前、監視開始時、出力回収前に `kaggle quota` を実行する。これは認証確認、現在の残量確認、期限切れアクセストークンの更新を兼ねる。成功後に `~/.kaggle/credentials.json` の `username`、`access_token_expiration`、`scopes` とrefresh tokenの有無だけを確認してよい。access token、refresh token、OAuth URLのcode、検証コードは端末出力、ログ、実験manifest、チャットへ出さない。現在のCLIは有効なrefresh tokenがあれば、API呼び出し時にアクセストークンを更新してcredentialsへ保存する。

`kaggle quota` が失敗し、複数のAPIコマンドでも認証要求が再現した場合は `kaggle auth login` を実行する。OAuth再認証にはブラウザでの承認と、表示された検証コードのCLI入力が必要になる場合がある。既存のKaggleログイン状態を使えるが、承認操作が必要ならその事実を明示する。取得したコードを画面やログに出さずCLIへ渡し、使用後はクリップボードを空にする。再認証後は `kaggle quota`、対象の `kernels status`、`kernels list --mine` の3つが成功することと、新しい有効期限を確認してから監視を再開する。

認証切れはKaggle上の実行を止めない。監視APIが失敗している間に、同じNotebookを再投入してはいけない。先に認証を戻し、元のslugの状態と最新実行時刻を確認する。slugはNotebook URLまたは投入時のmetadataに記録したものを使い、検索結果から推測しない。

2026-09-13には、Notebook側で一時的なDNS失敗によりPyPIへの接続が約3分再試行された例もあった。同じジョブの別実行では成功しており、`No matching distribution found` だけではパッケージ版不存在と断定できない。Kaggle metadataの `enable_internet: true`、DNS、必要なimport、CUDA/JAXデバイスを短い事前ジョブで確認する。今回のJAX実験はKaggle環境にある版を記録して使い、長時間ジョブの開始時に不要な最新版の取得を行わない。依存導入に失敗したジョブは学習失敗と集計せず、GPU枠の消費だけを記録する。

2026-09-14の着手前確認では、`kaggle quota` は成功し、GPUは30時間中9.61時間使用、20.39時間残りと表示された。その後、学習・シミュレーション・評価を投入するたびに再取得し、長時間のtest評価投入前は19.90時間残り、評価実行中の確認では19.69時間残りだった。過去の30時間やユーザーの概算を現在値として使わない。

15分ごとに `/kaggle/working/solo-search/` 配下へ、モデル・optimizer・乱数状態・進行ゲーム・未確定の教師データ・処理済み件数をまとめて保存する。確定した教師データも分割ファイルで保存し、最新50万配置の参照一覧と各データの学習・検証区分を保存する。ファイル名はrun IDとcheckpoint番号で一意にする。保存は一時ファイルからのrenameで確定し、サイズとSHA-256をmanifestに残す。

`/kaggle/working` に書いただけでは、セッションを失った後に回収できることの証明にはならない。最初の短いジョブを正常終了させ、CLIから出力を取得し、次のジョブへ入力として渡して再開できることまで確認してから長時間ジョブを実行する。通常は各ジョブを自主終了し、その出力を次の入力にする。直近15分以外の全てが必ず永続化されるとは仮定しない。

各runにはコミット、環境のライブラリ版、モデルハッシュ、全設定、seed区分、使用GPU、開始終了時刻、GPU枠消費見積もりを記録する。ゲーム記録はrun ID・game ID・turnで重複を判定し、再開前後の二重集計を防ぐ。

回収後は、ファイル件数・ハッシュ、期待ゲーム数、各ゲームの終了理由、連続手番号、発火履歴から再計算した集計の一致を検証する。途中失敗した実験を終了ゲームだけの結果にして報告しない。

## 11. Solの実装順と成果物

1. この文書から実験設定と評価器を作り、ツモ列・分割・基準v13の設定を固定する。死亡後の分母、発火効用、区間集計を小さな手作りイベント列でテストする。
2. 初期データの生成と旧AIの比較をCPUで進める。同時にJAX盤面処理をCPUで検証し、最小GPUバッチと出力回収を確認する。
3. MLPを学習し、JSへの書き出しと推論一致を確かめる。新しいJS探索を実装し、初期モデルの段階でブラウザ速度を測る。
4. GPUで生成と学習を反復し、実験予算とdev評価に従って停止する。
5. 構造比較と枝幅選択を終え、1候補を固定してtestを実行する。
6. ブラウザでリプレイと1手の待ち時間を確認し、採用条件を満たせば一人プレイの標準を切り替える。

実装ファイルは `src/ai/solo-search.js`、`src/ai/solo-value.js`、`training/solo_search/`、`tools/evaluate-solo-search.js` を基本にする。ゲームルールの参照実装は既存coreを使う。モデルと生成データは別に保存し、大量データをGitへ追加しない。着手前に変更対象と各変更の理由を示し、意味のある区切りで進捗・判断・検証結果を実験報告へ追記する。

最終成果物は、動作する新探索、再実行できるKaggleジョブ、ブラウザ用モデル、seedと設定のmanifest、実イベント記録、比較結果、速度計測、再開方法とする。リプレイは事前固定したseedに加え、最高連鎖・連発失敗・死亡の例も残す。都合のよい成功例だけで採用を説明しない。

この計画の中でSolが調整してよいのは、実測に応じたGPUバッチ数、生成量、既定の候補内のBeam Width、CPU並列数である。報酬、NEXT数、test分割、採用条件を変更する必要が生じた場合は、理由と影響を記録し、変更後は別の実験として扱う。

## 12. 実行後の補足

初期学習モデルだけを使ったJAXのdev 64ゲーム×1,000手では、10連鎖以上が0件だった。そのため、学習モデルだけで完成とせず、実行時に構造事前評価を組み合わせた候補を別に測定した。構造事前評価は旧vシリーズを呼び出さず、`solo-search` 内の盤面特徴だけで計算する。固定dev 4ゲーム×300手ではBeam 22の中央値170.96ms、p95 283.66ms、Beam 32の中央値351.93ms、p95 559.23msだったので、UIの既定値は22へ変更した。どちらも小規模な開発測定であり、最終testの採用条件を満たした証拠ではない。

同じ4ゲーム×300手の旧v13標準はU1000 14.7917、中央値353.22ms、p95 493.77msだった。この比較では新系統の速度は改善したが、連鎖能力の改善は確認できていない。性能条件を満たしたと誤って扱わず、固定testの結果と限界を別に報告する。

全体の `node --test` は118件すべて成功し、ppsim2では設定画面から `Solo Search` とBeam 22を選べ、AI一手の実行まで確認した。モデル単体のGPU評価で10連鎖以上が0件だったため、Solo Searchを旧v13の代替標準へ自動切り替えず、選択可能な候補として残す。今後の改善では、構造事前評価を含む経路をGPU評価へ移すか、追加教師データを作ることが必要になる。

重い固定test 128ゲーム×1,000手のJAX評価は、モデルとPython実装を含む非公開Kaggleデータセットへ固定し、T4カーネル `ikakun624/puyoai-solo-search-evaluation` で実行した。2枚のT4で1,792.65秒、128,000手を完了し、死亡0、10連鎖以上0件、最高連鎖1だった。GPU評価は学習モデル単体のJAX経路を測るため、構造事前評価を含むブラウザ経路とは指標を分けて記録した。モデル、test seed、回収トレースのSHA-256は実行レポートとローカル再計算で一致した。
